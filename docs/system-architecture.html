BricksBot System Architecture

A greenfield, enterprise-grade Databricks App designed in the Grok Bot product shape: multi-bot team spaces, durable conversational agent harnesses, lakehouse-native tools, 3-way approvals, autonomous routines, and secure compute execution.

1. System Overview

BricksBot is built directly on top of Databricks AppKit (Express + React 19). It runs directly inside a Databricks workspace as an isolated containerized service, authenticating users via Databricks OAuth reverse proxy, and using Databricks PostgreSQL (Lakebase) for ACID persistence.

Lakehouse Native

Runs ANSI SQL against SQL Warehouses, inspects catalogs via Unity Catalog, and reads volumes without data leaving the perimeter.

Multi-Agent Roster

Primary router bot bootstrapped on first login, with durable handoffs to domain bots created on-demand, by Primary, or installed from the Marketplace.

Human-in-the-Loop Trust

Ask-first tool approvals (Once / Always / Deny), choice prompts, and automated routine audit logs.

Isolated Multi-User Tenancy

Personal bot spaces, shared team spaces with strictly private per-user chat sessions, and a company-wide bot marketplace.

3. Multi-User Tenancy & Data Governance

BricksBot enforces complete user-level multi-tenancy. Multiple users can share the same Databricks App deployment without cross-contaminating private chats, credentials, or prompts.

Tenancy Model Overview

Domain Storage Entity Tenancy & Isolation Rule
Personal Space bricksbot.spaces Bootstrap creates a Personal space per user (owner_id = userId). Inaccessible to all other users.
Primary Bot bricksbot.bots Each user has their own Primary router bot. Primary bots are non-shareable, non-deletable, and bound to the owner.
Shared Space Bots bricksbot.space_members Bots created in shared spaces are visible to space members, but bot ownership stays with the creator.
Per-User Chat Threads bricksbot.chats Enforced by UNIQUE (bot_id, user_id). User A and User B talking to the exact same bot get completely isolated chat threads.
Roster Previews bot.lastPreview Dynamically computed per user. User A's private queries are never visible on User B's roster card.
API Route Protection /api/chats/:chatId/* assertChatOwnership returns 403 Forbidden if a caller attempts to post messages or inspect approvals of another user's chat.
Marketplace Sharing /api/marketplace/bots Only the creator can publish a bot. Installing clones instructions and skills into the caller's personal space, zeroing out private memories and chats.
Airtight Isolation Proof: Automated tests in server/chat/routes.test.ts and server/chat/lakebase-store.test.ts verify that cross-user chat injection, roster leaks, and unauthorized approval mutations are rejected with 403 Forbidden.

4. Thin Pi-Compatible Agent Harness

The agent loop is modeled after Earendil's Pi Durable framework, built specifically for transactional Postgres/Lakebase state machines.

Turn Execution Lifecycle

  1. Request Ingestion & Idempotency: Client sends message with optional requestId. If already processed, cached response is returned immediately.
  2. History Replay Validation: Builds OpenAI-compatible message history. Every assistant turn containing tool_calls is guaranteed to be paired with subsequent matching tool results before making LLM calls.
  3. Model Completion: Calls the configured provider (OpenRouter or Databricks Model Serving).
  4. Tool Execution & Sibling Waiting:
    • Auto-approved Tools (meta tools, catalog inspect): Execute immediately within the turn.
    • Ask-first Tools (SQL, sandboxes, routine delete): Generates pending approval rows; suspends turn; sets bot presence to waiting.
    • All sibling tool calls in an assistant response must complete before the agent loop triggers the next LLM turn.
  5. Transcript Compaction: When context grows large, summarizes older conversation turns into a durable summary row while never destructively dropping raw message history.

5. Capability & Tool Catalog

Tools are registered dynamically in ChatService using a capability catalog that formats system prompts with tool definitions and instructions.

Tool Name Trust Policy Target & Purpose
sql_query Ask-First (Configurable) Executes ANSI SQL queries against Databricks SQL Warehouses via Statement Execution API with row limits.
lakehouse_catalog Auto-Run Discovers Unity Catalog metadata: catalogs, schemas, tables, views, and column schemas.
volume_read Auto-Run Reads text, CSV, JSON, and tabular data files stored in Unity Catalog Volumes.
web_fetch Auto-Run Fetches external web pages subject to a strict secret-backed domain allowlist (bricksbot/web-fetch-allowlist).
handoff_to_bot Primary Only Dispatches intent to a teammate bot, runs a nested turn, and posts a clickable peek chip.
create_bot Ask-First (Always) Dynamically provisions a new specialist bot into the space with custom instructions.
pin_artifact Ask-First Embeds code files, SQL scripts, or analysis markdown in the UI's persistent right-side panel.
pin_chart Ask-First Renders interactive Vega / Vega-Lite data charts (bar, line, scatter) from query results.
ask_choice Ask-First (Always) Pauses execution and displays clickable option buttons for the user to select from.
activate_skill / save_skill Auto-Run Loads domain instructions into context; allows bots to persist newly acquired skills.
remember / forget Auto-Run Manages durable per-bot long-term key/value memory storage.
sandbox_exec Ask-First Executes shell commands or Python scripts inside isolated compute sandboxes.

Built-in Seed Skills (Available Out-of-the-Box)

In addition to tools, every bot has access to 5 built-in lakehouse skills defined in shared/agents/seed-skills.ts. These guide the agent on how to sequence tools, apply limits, and validate answers:

Seed Skill Name Trigger Context Operational Guidance
sql-explore Lakehouse data queries Enforces single read-only queries (SELECT/DESCRIBE), requires LIMIT (20–100), and mandates citing exact SQL and table identifiers in replies.
catalog-recon Metastore exploration Directs the bot to map catalogs → schemas → tables → columns, summarize fact vs. dim relationships, and offer verified follow-up queries.
weekly-table-health Data quality & freshness Calculates row counts, freshness latency, and null rates; reports explicit pass/warn/fail thresholds; recommends automation as a routine.
pin-finding Shareable insights Extracts key findings (SQL snippets, table summaries, volume paths) and pins them to the transcript right-side rail using pin_artifact.
dataviz Charts & distributions Transforms tabular query rows into interactive Vega-Lite v6 specifications (bar, line, scatter) rendered via pin_chart.

6. Human-in-the-Loop Approvals

BricksBot implements a durable 3-way approval flow. When an Ask-first tool is planned, the turn pauses and persists an approval record.

1. Approve Once

Authorizes the single invocation. The turn resumes and records the decision timestamp in Lakebase.

2. Always Allow (Chat Scoped)

Adds tool to auto_approvals for that chat. Subsequent calls run without prompt. Revocable anytime from UI chips.

3. Deny Request

Rejects tool execution. Generates a synthetic tool error row, allowing the LLM to recover gracefully or apologize.

Strict Guardrails: High-risk tools like create_bot, delete_routine, and ask_choice can never be marked as "Always allow" and always require explicit approval per occurrence.

7. Autonomous Routines & Lakeflow Webhooks

Routines enable background execution of bot prompts on cron schedules or external event triggers.

Key Capabilities

  • Cron Execution: Managed through Databricks Lakeflow jobs or native scheduler triggers.
  • SHA-256 Webhook Auth: Each routine generates a unique webhook endpoint protected by a cryptographic token hash. Requests send the secret via X-BricksBot-Webhook-Key or Bearer authorization.
  • Audit Logging & Trust Badge: The UI displays last run status, execution time, and trust indicators.
  • Owner Scoping: Routines are bound to the creator's owner_id. Users cannot see or trigger each other's routines.

8. Phase 5 Compute Sandboxes

BricksBot supports executing untrusted code or complex data transformations in isolated Linux execution environments.

Supported Backends (SANDBOX_BACKEND)

Databricks Sandboxes (Beta)

Native Databricks-managed ephemeral containers with seamless workspace identity.

Python Exec Fallback

Executes via system.ai.python_exec when Databricks Sandboxes Preview is disabled.

E2B Containers

Isolated cloud sandboxes with full Linux terminal, filesystem, and package installation.

Sandboxes automatically sync generated artifacts (charts, CSV reports) into Unity Catalog Volumes at /Volumes/main/default/bricksbot_artifacts.

10. Bundle & Deployment Operations

BricksBot is deployed as a Databricks Asset Bundle (DAB) using the Databricks CLI.

Build & Deploy Commands

# 1. Run local checks (Typecheck + 252 Vitest unit tests)
npm run check

# 2. Build TypeScript backend and Vite frontend
npm run build

# 3. Validate & deploy bundle files to Databricks Workspace
databricks bundle validate -p dev
databricks bundle deploy -p dev

# 4. Deploy & restart App compute container
databricks bundle run app -p dev
# Or direct app deployment:
databricks apps deploy bricksbot -p dev
Pre-commit Guard: A git pre-commit hook (.githooks/pre-commit) is configured via npm run prepare to automatically run npm run check prior to every commit, preventing type regressions or broken tests from reaching source control.
